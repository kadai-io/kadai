# Green Metrics Tool

We are using the [Green Metrics Tool (GMT)](https://www.green-coding.io/products/green-metrics-tool/) to measure the resource and energy consumption of typical usage scenarios of KADAI.

GMT Documentation: <https://docs.green-coding.io>

Design decisions for this setup are documented in [DECISIONS.md](./DECISIONS.md).

## Setup

* GMT for measuring the resource and energy consumption
* [k6](https://k6.io/) for the automation (calls different API endpoints of the KADAI backend)
* PostgreSQL as the database for KADAI
* [kadai-gmt](../../rest/kadai-gmt) as the target subject (built from [rest/kadai-gmt/Dockerfile](../../rest/kadai-gmt/Dockerfile))

### Scenarios

* [usage_scenario_quick.yml](./usage_scenario_quick.yml): test/debug scenario, uses the moving `latest` image, seeds 1000 tasks
* [usage_scenario_standard.yml](./usage_scenario_standard.yml): regular energy measurements, pins a `sha-<commit>` image that CI bumps automatically, seeds 100000 tasks
* [usage_scenario_blue_angel.yml](./usage_scenario_blue_angel.yml): "Blauer Engel for Software" certification, pins a frozen image tag derived from the certification branch (and the postgres/k6 images), seeds 100000 tasks

Only the quick scenario uses the moving `ghcr.io/kadai-io/kadai-gmt:latest` image; the standard scenario
pins a `sha-<commit>` tag (auto-bumped by CI), while the certification scenario pins the
`blauer-engel-v<version>` image tag of the certification branch (changed manually per measurement).
Available application image tags are published on the [kadai-gmt package page](https://github.com/kadai-io/kadai/pkgs/container/kadai-gmt).

### Database Filling

The task test data is generated by the `kadai-gmt` image in a short-lived child JVM inside the `app`
container, before the measured application starts (`java -jar kadai-gmt.jar --generate-tasks=N`, see
[DECISIONS.md](./DECISIONS.md)). The child JVM exits once the data is committed, so the generator's
heap, JIT code and class metadata never reach the measured JVM. Generation runs during GMT's
`[BOOT]` phase and is therefore not part of the runtime measurement. The number of tasks is
controlled by the `GENERATE_TASKS` environment variable (`100000` for the standard and certification
scenarios, `1000` for the quick scenario, `0` disables generation).

The endpoint `POST /kadai/api/v1/gmt/tasks` still exists for manual seeding against a running
application.

## Local Execution (Testing)

Local execution is only relevant for testing purposes. To make representative measurements, use the [Measurement Cluster](#measurement-cluster-real-measurements) (see below).

Install GMT: <https://docs.green-coding.io/docs/installation/>

Start GMT (ensure you are in the directory where GMT was installed):

1. `docker compose -f docker/compose.yml up -d`
2. `source venv/bin/activate`

You can either run a local measurement using a cloned KADAI repository on your local filesystem or using the remote URI:

* using cloned repository (change the path "$HOME/kadai" if necessary):
  
  ```sh
  python3 runner.py --name "KADAI REST Application (quick)" --uri "$HOME/kadai" --filename "qa/gmt/usage_scenario_quick.yml" --skip-unsafe --skip-optimizations --dev-no-system-checks --dev-no-sleeps
  ```

* using remote URI:
  
  ```sh
  python3 runner.py --name "KADAI REST Application (quick)" --uri "https://github.com/kadai-io/kadai" --filename "qa/gmt/usage_scenario_quick.yml" --skip-unsafe --skip-optimizations --dev-no-system-checks --dev-no-sleeps
  ```

Used [runner switches](https://docs.green-coding.io/docs/measuring/runner-switches/):

* `--skip-unsafe`: Skips unsafe compose contents like ports mappings.
* `--skip-optimizations`: Skips the creation of potential optimization recommendations (not relevant for testing the usage scenario).
* `--dev-no-system-checks`: Skips checking the system if the GMT can run (not relevant for testing the usage scenario).
* `--dev-no-sleeps`: Removes all sleeps (measurement run is faster, but resulting measurement data will be skewed).

## Measurement Cluster (Real Measurements)

A new measurement on the measurement cluster can be triggered via:

* the UI: <https://metrics.green-coding.io/request.html>
* the API: <https://api.green-coding.io/docs#/default/software_add_v1_software_add_post>

For easier use of the API you can use the script [./scripts/submit_software.py](./scripts/submit_software.py). See the [./scripts/README.md](./scripts/README.md) for more information.

We use the machine "CO2 Benchmarking 2.0 - TX1330 M2 [PREMIUM]" (GMT machine ID 14), because this machine is tuned for reproducability. Since the 2026 re-measurement a RAPL power limit (`power_limit_uw`) of 25 W is configured, and 1 CPU core plus 2 GiB RAM are reserved for the system. Details about the machine can be found in the [GMT documentation](https://docs.green-coding.io/docs/measuring/measurement-cluster/).

The results of the runs that we made public can be seen here:
<https://metrics.green-coding.io/runs.html?name=KADAI&show_archived=false&show_other_users=true>

## Blauer Engel Certification

The measurement setup for the "Blauer Engel for Software" certification is defined in the GMT usage scenario file [usage_scenario_blue_angel.yml](./usage_scenario_blue_angel.yml).

The scenario is split into three phases:

1. **Warm-up:**: [k6/blue_angel/1_warm_up.js](./k6/blue_angel/1_warm_up.js)

   * primes the JVM (JIT) and caches so that the subsequent measurement reflects steady-state behavior

2. **Pause:** [k6/blue_angel/2_pause.js](./k6/blue_angel/2_pause.js)

   * provides a clearly separated time window between phases (useful for charts/notes and avoiding cross-contamination of metrics)

3. **Standard usage scenario (actual measurement)**: [k6/blue_angel/3_standard_usage_scenario.js](./k6/blue_angel/3_standard_usage_scenario.js)

   * realistic, parallel-user workflow covering the everyday task lifecycle (create, read, edit, assign/claim, move, comment, complete), workbasket operations (search/open), and a single monitoring report
   * steps are synchronized with short gaps to aid interpretation
